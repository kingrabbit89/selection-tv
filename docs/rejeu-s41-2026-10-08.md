# Rejeu de la fabrication réelle de S41

Ce travail répond à une question concrète : peut-on exploiter un numéro déjà réalisé pour éprouver et améliorer la production, sans attendre qu'un nouveau numéro soit terminé ? **Oui.** Git conserve les choix, textes, images, pools, sources et corrections de S41. Un rejeu de ces données permet de mesurer la mécanique, de retrouver l'ordre des étapes et de localiser les données manquantes. Il complète une mesure de recherche sur une nouvelle semaine.

Le cas est figé sur `2c661aaf235903f4a98ffc02e115ca7864892bb9`. Les heures ci-dessous sont les jalons Git du 27 septembre 2026 en Europe/Paris, pas des durées de travail actif. La simulation reste séparée de la production ; elle n'ajoute aucune consultation de source, ne certifie aucune diffusion et ne publie rien.

## Reproduire le rejeu

Le script `scripts/replay-historical-editorial.mjs` lit une semaine publiée à un SHA immuable. Il restitue ses pages et fichiers, puis soumet les décisions récupérables au générateur actuel dans un contexte exclusivement local. Les refus apparaissent dans le rapport. Une date de relecture technique n'est jamais une date de consultation de source. Le dossier de sortie doit être neuf et situé hors de tout checkout Git.

```sh
node scripts/replay-historical-editorial.mjs 2026-S41 2c661aaf235903f4a98ffc02e115ca7864892bb9 /tmp/s41-rejeu-neuf
node --test scripts/test-replay-historical-editorial.mjs
```

Il faut disposer du commit source dans le clone local ; la CI du projet récupère l'historique complet. Les trois nouveaux tests utilisent ce SHA figé, pour que les enrichissements des numéros suivants ne modifient pas le cas de référence. Ils passent avec les huit tests existants du générateur de rubriques.

Le rejeu tente 128 positions : 86 dans les pools, 22 articles de rubriques hors pools et 20 positions radar. Certaines œuvres apparaissent plusieurs fois ; ce ne sont pas 128 œuvres distinctes. Dix entrées sont compatibles avec le rendu actuel, 118 sont refusées et aucun des neuf pools n'est entièrement compatible. Les champs visibles dans l'ancien HTML peuvent être conservés sans être suffisamment structurés pour une entrée dans le générateur. Le rapport distingue la restitution de l'archive des essais du contrat actuel. Un refus peut demander une conversion de format ou une preuve manquante ; il ne signifie pas nécessairement que le fait est faux ou inconnu. Les sondes individuelles n'ont pas valeur de nouvelle sélection éditoriale.

Les preuves compactes sont dans [replays/s41-rendering.json](replays/s41-rendering.json) et [replays/s41-validation.json](replays/s41-validation.json) : SHA, empreintes, durées, préservation des fichiers et classes de refus.

### Reproduire les profils de validation

Créer deux copies isolées et neuves à partir du SHA source :

```sh
git worktree add --detach /tmp/s41-validation-historique 2c661aaf235903f4a98ffc02e115ca7864892bb9
git worktree add --detach /tmp/s41-validation-stricte 2c661aaf235903f4a98ffc02e115ca7864892bb9
```

Dans la seule copie `/tmp/s41-validation-stricte`, modifier l'enveloppe et les dates d'activation comme suit : `manifest.latest=2026-S40`, statut de l'entrée S41 et `publication_status` S41 à `draft` ; `strict_inventory_from_week`, `strict_section_targets_from_week` et `remote_image_health_from_week` à S41 dans `editorial-config.json` ; `freshness.enabled_from_week` et `reserve_readiness.enabled_from_week` à S41 dans `personalization-config.json`. Conserver tous les autres champs et fichiers, notamment les pages et pools.

Exécuter dans chaque copie les sept scripts `validate-canonical-identities`, `validate-architecture`, `validate-publication-candidate`, `validate-editorial`, `validate-links`, `validate-freshness` et `validate-reserves`, avec Node. Fixer `SELECTION_TV_TODAY=2026-10-02` et vider les variables de contexte de candidate pour le profil historique. Pour le profil strict, ajouter `SELECTION_TV_VALIDATE_WEEK=2026-S41`, `SELECTION_TV_CANDIDATE=1` et `GITHUB_HEAD_REF=auto/2026-S41`. Aucune modification de ces copies ne doit être importée dans les données de production : elles servent uniquement à comparer les contrats sur le même contenu.

## Méthode à réutiliser pour la production

Le rejeu permet de placer toutes les étapes dans une seule chaîne de travail, en réutilisant les outils existants :

1. Figer l'inventaire et les preuves déjà acquis ; produire une présélection par jour et rubrique, en conservant les exclusions importantes.
2. Rapprocher cette présélection du catalogue. Réutiliser les métadonnées valables, puis rechercher seulement les champs absents, les versions ambiguës et les événements propres à la nouvelle semaine.
3. Écrire ensemble les choix et leurs réserves, avec synopsis, motifs, liens et provenance. Un checkpoint sauvegarde ce lot ; il ne termine pas nécessairement le passage.
4. Donner ces décisions explicites au générateur de cartes et rubriques ; il construit le JSON, les grilles, le sommaire et la couverture.
5. Contrôler le lot, regrouper les écarts par cause commune, corriger, puis poursuivre le lot suivant. Terminer par les images, le rendu et les contrôles de publication.

Cette séquence réduit les retours sur les mêmes dossiers et les réparations après assemblage. Elle ne demande pas une pause horaire entre chaque étape : les reprises planifiées servent à reprendre un travail interrompu. Pour mesurer son efficacité, il faut enregistrer les durées des étapes et les livrables obtenus, ainsi que la cause précise d'un arrêt.

Le rejeu historique constitue un test réaliste de l'assemblage et des contrôles sur des données éditoriales véritables. Les recherches non enregistrées ne peuvent pas être recréées comme si elles avaient été exécutées. Une mesure sur quelques dossiers nouveaux permettra ensuite d'ajouter le coût de recherche à cette base mesurée ; il n'est pas nécessaire d'attendre un numéro complet pour améliorer et tester le processus.
